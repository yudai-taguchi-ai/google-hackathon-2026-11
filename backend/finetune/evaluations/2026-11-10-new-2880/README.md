# 追加テスト2,880件：3方式の比較と内容分析

2026-11-10にPCのCPUで実施。対象は [`test.jsonl`](../../data/test.jsonl) の**先頭400件の後に追加された2,880件**。英語・中国語・韓国語が各960件で、日本語は含まない。正答は関数名と引数の両方が正解ラベルと一致した件数。以前の400件だけの結果と異なるテスト集合なので、点数の上下をそのまま性能の変化とは言えない。

## データの背景

[プロジェクトのREADME](../../../../README.md) と [PR #47](https://github.com/yudai-taguchi-ai/google-hackathon-2026-11/pull/47) によると、追加分は災害時の場面を想定した少数の基本文に、呼びかけや句読点を組み合わせた合成データ。人が手書きした約50件から**直接**作成されたかは未確認。

追加分を、各言語の冒頭の呼びかけ4種類と末尾の句読点だけを除いて整理すると、**162グループ（各言語54）**になった。この集計は今回の文字列処理によるグループ分けであり、作成元の基本文IDではない。各グループには10件または20件の表記がある。したがって、2,880件をすべて独立した場面とは考えられない。実際の音声認識の誤変換や、未登場の言い方で同様の性能になるとは限らない。

## 結果

| 指標 | ルール | BERT | FunctionGemma |
|---|---:|---:|---:|
| 正答率（2,880件） | 64.24%（1,850件） | 86.60%（2,494件） | **95.38%（2,747件）** |
| 危険ケースの取りこぼし（既存定義・960件） | 36.46%（350件） | 6.35%（61件） | **2.29%（22件）** |
| 危険ケースの全不一致（960件） | 37.50%（360件） | 11.56%（111件） | **4.90%（47件）** |
| 関係ない発話での誤作動（既存定義・360件） | **0%（0件）** | 3.06%（11件） | 6.94%（25件） |

| 正答率 | ルール | BERT | FunctionGemma |
|---|---:|---:|---:|
| 英語（960件） | 78.12% | 82.08% | **95.73%** |
| 中国語（960件） | 58.33% | 92.29% | **97.81%** |
| 韓国語（960件） | 56.25% | 85.42% | **92.60%** |

「危険ケース」は、遅い移動・車いす等・けが・道の通行止め。**既存の取りこぼし**は、正解が危険ケースなのに `other` または `reselect(normal)` としたものに限る。「全不一致」は関数名・引数が一致しなかったすべてで、別の危険ケースへの誤判定や解析失敗も含む。全不一致のすべてが同程度に危険という意味ではない。[採点コード](../../score.py) の誤作動率は、正解が `other` の場合に `other` と `repeat` 以外を返した割合であり、`repeat` への誤分類は含まれない。

## 内容を見た分析

- **FunctionGemmaは総合で最も高いが、無関係な発話への反応に課題が残る。** 既存の目標は、危険ケースの取りこぼし2%以下、関係ない発話での誤作動3%以下。今回の2.29%と6.94%はどちらも未達。例えば英語の「What time is it now」（今何時？）20件のうち7件を `when_to_return` と判定した。一方、「What is your name」（名前は？）20件のうち17件は `repeat` と判定したが、上記の誤作動率には含まれない。
- **危険な内容でも、基本文ごと間違える例がある。** FunctionGemma は英語の「My child cannot run, pick a closer shelter」（子どもが走れないので近い避難先を選んで）10件すべてを、正解の `reselect(slow)` でなく `reselect(normal)` と判定した。また、韓国語の「隣の人がひどく切り傷を負った」20件はすべて `injured` 以外だった。前者は取りこぼしに含まれるが、後者は `lost_family` や `road_blocked` への誤分類もあり、既存の取りこぼし指標だけでは全件を捉えない。
- **韓国語では、似た表記でも文脈により意味が変わる例に注意が必要。** `다리` は文脈によって「橋」または「脚」の意味になる。今回、橋が閉鎖された文をけがと判定する例がFunctionGemmaにもあり、単語だけでなく文全体の理解を確認する必要がある。ただし、このデータだけで誤りの原因を断定はできない。
- **BERTは言語・分類で差がある。** 中国語は92.29%だが英語は82.08%。全言語では `reselect(slow)` が60.83%、`when_to_return` が63.89%だった。例えば英語の「近くの人がひどく切れた」という文20件はすべて `other` だった。
- **ルール方式は呼びかけ・句読点を除いた162グループのうち、106グループで全件正解、56グループで全件不正解だった。** 設定された語に一致するかどうかが繰り返しの表記に反映されることを示している。FunctionGemmaは149グループが全件正解、4グループが全件不正解、9グループは表記によって結果が分かれた。グループの大きさは同じではないので、この数を正答率として扱わない。

各方式の出力は避難先を直接確定させず、既存アプリの確認操作・ボタンでの代替と合わせて扱う。モデルをこのテストデータに合わせて調整する場合は、性能の最終確認に使う新しい未使用データを別に用意する。人が実際に話し、音声認識を通した文での評価が次に必要。

## 評価条件・再採点

- ルール: `finetune.score.keyword_baseline`。Androidのルールを同じ2,880件に適用した結果と全件一致した。
- BERT: 追加学習済み多言語BERTのONNX、ONNX Runtime CPU。旧400件の保存済み予測と、再読み込みしたONNXの予測が全件一致。モデルSHA-256: `64ef89d50f0851f7da33a87fd0eb8f1a554f839260ce1ea7124a883399f4b83b`。トークナイザSHA-256: `68376ce5e989db0c0bdb282422a99e12e449c1f97a1a18daf705626db0d57b83`。
- FunctionGemma: 追加学習・変換後の `.litertlm`、LiteRT-LM 0.18.0 CPU、top-k 1。旧テストの先頭20件は保存済み予測と一致。モデルSHA-256: `c90233ffdb2e9fdea4a2ec703591922d6557a0447de418a53d3ad2587b04de4b`。プロンプトは `android/app/src/main/assets/intent_prompt.txt`（SHA-256 `f4321fa4cc5874d69d6a85803858c72fe90e92a7b607d6cafd19c9c30df7f98e`）。推論は複数区間に分けて実施し、元の順序に結合した。
- Android実機での推論、音声認識、処理速度は未測定。PCでの並列処理時間を端末速度には使わない。
- 予測は `rule.jsonl`・`bert.jsonl`・`functiongemma.jsonl` に追加分と同じ順序で保存。モデル・発話・個人情報は含まない。テストファイル全体のSHA-256: `2296d2367b078ae1ab668fdf1ccf06a0846743e5883db79caf0a724c7c7789f0`。

リポジトリの `backend/` で以下を実行すると、保存した予測を `finetune.score` で再採点できる。テストファイルが変わった場合はハッシュの確認で停止する。

```sh
python -X utf8 finetune/evaluations/2026-11-10-new-2880/verify.py
```
