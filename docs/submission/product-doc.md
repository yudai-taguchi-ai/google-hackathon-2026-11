## 1. プロダクト名
津波避難ナビ（旅行者向け）【仮。名前は要決定】

## 2. カテゴリ
観光（対象：日本を訪れる外国人旅行者）

## 3. 解決する課題
- 日本で大きな地震が起きると、津波警報が出てから到達まで数分〜数十分しかないことがある。土地に不案内な旅行者は、どこへ逃げればよいか分からない
- 市町村は「津波のときに使える避難場所」を決めて公開しているが、日本語の一覧や地図で、旅行者には届きにくい。観光庁の Safety tips は警報の通知と流れ図が中心で、今いる場所からの避難先の案内はしない
- 生成 AI に聞くと、それらしい答えが返るが、間違いが混ざる。大阪市・堺市の 30 地点で、Gemini（Google 検索・Google マップの裏付けつき）に「大津波警報・到達まで 17 分・徒歩」で避難先を聞き、公式データで採点した（7 章）。挙げた場所の多くは公式の避難場所だった（3.8 Flash で 84%）が、**歩く時間を大きく短く見積もった**（Gemini が言った時間の平均 6.2 分 → 実際の道のりを 0.62m/秒で歩くと平均 24.4 分。1.0m/秒でも約 15 分。60 件中 55 件で実際が 1.5 倍を超えた）。その結果、**1 番目に挙げた場所が公式の避難場所で、かつ間に合う**のは 3.8 Flash で 47%、Argon で 30% だった。浸水が想定される公園を「浸水しない高台」と案内した例も 3 件あった
- 災害時は通信がつながりにくくなる。能登半島地震（2024年）では最大 839 の携帯基地局が止まった。データ通信を持たない旅行者もいる

## 4. 解決策（何ができるか）
強い揺れを感じた時や警報が出た時、旅行者の今いる場所から、**市町村が決めた津波の避難場所のうち、間に合う所**を選び、英語の声と画面で案内する（画面は英語＋日本語。Gemini Live では相手の言語で話せる）。通信が落ちても、端末の中だけで案内を続ける。使い方ごとの動きは docs/modes.md

| 場面 | できること |
|---|---|
| 旅行の前（宿の Wi-Fi） | 行き先（大阪湾岸）のデータ一式を端末に保存（避難先 2,335 件・浸水想定・答えの音声、約 1MB） |
| 警報（通信あり） | アプリが 15 秒ごとに警報を確かめ、出ていれば自動で案内を始める（デモは気象庁の訓練電文の流し直し）。到達予想時刻と Routes API の道のりから「間に合う避難先」を選ぶ。Navigation SDK でアプリの中で目的地まで徒歩の案内。Gemini Live に話しかけると、選び直しや質問に声で答える |
| 圏外・機内モード | 「揺れた」ボタンだけで、保存したデータから 3 秒以内に避難先を出し、方角の矢印と距離、声で案内する。到達時刻は「揺れた時刻＋26 分」（大阪府の想定で一番早い値）を目安に使う |
| 困ったとき | 「子どもが走れない」と言うと（またはボタン）、歩く速さを 0.5m/秒にして、近い避難ビルに選び直す。圏外ではボタンで受ける（端末の中の小さい AI＝FunctionGemma を追加学習中。評価の物差しは docs/finetune-eval.md） |

決めごと（安全のため）
- 避難先を AI に決めさせない。名前・場所・階は公式データの値だけを使い、AI は説明と頼みごとの聞き分けだけをする
- 歩く速さは東日本大震災の実際の平均 0.62m/秒（消防庁の報告書）。歩くのが難しい時は 0.5m/秒
- 建物へ逃げる時は 3 階以上（堺市の津波避難ビルの指定基準）

## 5. Google 技術の活用と選んだ理由
| 技術 | 使い方 | 選んだ理由・比べた案 |
|---|---|---|
| Cloud Run | サーバー（警報・避難先の計算・パック）と Web 版 | 使う時だけ動き、コンテナで載せられる。審査員が触れる Web 版も同じ所で出せる |
| Vertex AI（Gemini 3.8 Flash） | 選んだ避難先の説明・答えの翻訳・音声の生成 | 候補の外の場所を言わせない作り（候補の id 以外を使ったら捨てて決まった文にする）。AI Studio ではなく Vertex AI にしたのは、GCP のクレジットが効き、キーをアプリに置かないため |
| Firebase AI Logic（Gemini Live）＋ App Check | 通信がある時の声の会話。頼みごとは関数で受け取り、アプリが公式データで選び直した結果だけを話す | アプリから直接、低い遅れで声の会話ができる。キーを埋めず App Check で守れる。比べた案：Cloud Run の中継（遅れが増える） |
| Routes API | 徒歩の道のり・別の候補の道。浸水想定の深い所を通らない道を選ぶ | 直線距離では「間に合うか」を誤る。既存の避難アプリ（広島市・三重県・横浜市）は道順と浸水の地図の重ね表示までで、浸水を避けて道を選ぶものは見つからなかった |
| Navigation SDK | 通信がある時のアプリの中の徒歩の案内（目的地まで。浸水の浅い道を経由地で渡すのは今後） | Google マップに移ると会話が途切れ、事前の地域データも渡せない。案内開始時に 15〜20 分ぶんの経路を保存するので、途中で圏外になっても続く見込み |
| FunctionGemma 270M ＋ LiteRT-LM | 圏外の時、端末の中で頼みごとを聞き分ける（追加学習中。今のアプリはボタン） | 圏外では Gemini が使えない。仕事は「8 種類の頼みごとから選ぶ」だけなので小さいモデルで足り、多くの旅行者のスマホで動く（Gemma 4 E2B 約 2.5GB は多くの端末で動かない）。Gemini で 4 言語の学習データを作って追加学習した |
| Secret Manager | Routes API のキーの保管 | キーをコードに置かない |

## 6. AI をどの場面でどう使ったか・なぜその場面か（必須記入）
- **説明（Gemini 3.8 Flash）**：アプリが公式データから選んだ避難先を、旅行者の言語で短く説明する。場所を選ばせないのは、試験で Gemini 単体が歩く時間を短く見積もったり、浸水する場所を高台と言ったりしたため。言葉を整えることは得意なので、そこだけを任せた
- **声の会話（Gemini Live）**：慌てている時は画面を読めない。浜辺での実験で、アプリを見ながら歩くと遅くなるという報告もある。声で頼みごとを受け、関数でアプリに選び直させる
- **翻訳と音声の生成（Gemini）**：圏外でも流せるよう、答えの文と音声を旅行の前に作って保存する
- **学習データづくり（Gemini）と端末の中の AI（FunctionGemma）**：圏外では大きな AI が使えないので、Gemini を先生にして 4 言語・1,600 件の言い方を作り、小さいモデルを追加学習した。学習前後の正答率：【Colab の結果を入れる】
- **評価（Gemini）**：大阪市・堺市の 30 地点で、Gemini 単体に同じ質問をし、公式データで採点した（6 章の表）

## 7. 評価の結果
| 指標 | Gemini 3.8 Flash | Gemini 4 Argon | このアプリ |
|---|---|---|---|
| ① 挙げた場所が公式の津波避難場所 | 76/90（84%） | 57/89（64%） | 30/30（100%） |
| ② 名前と位置が公式と合っている | 75/90（83%） | 49/89（55%） | 30/30（100%） |
| ③ 浸水想定区域の中を「高台・区域の外」と案内した数 | 2 | 1 | 0 |
| ④ 1 番目の避難先までの歩く時間（アプリとの差） | 平均 +6.0 分 | 平均 +7.0 分 | 0 |
| ⑤ 1 番目が公式の避難場所で、かつ間に合う | 14/30（47%） | 9/30（30%） | 20/30（67%） |

- 30 地点＝観光地・駅 12（海遊館・USJ・堺駅など）＋浸水想定区域の中から無作為に 18。正解データは国土地理院の指定緊急避難場所（津波）と国土数値情報の浸水想定（大阪府）
- アプリは公式データから選ぶ作りなので ①〜③ は作りの上で満点。差が出るのは ④⑤（間に合うか）
- アプリでも 10 地点は「間に合う避難先が無い」と判定した（USJ・浜寺公園など）。その時は一番近い頑丈な建物の上の階へ、と案内する
- 結果の全データ: backend/eval/results/
