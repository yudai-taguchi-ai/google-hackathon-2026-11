## 2026-11-07 避難先は Gemini に選ばせない

- 捨てた理由: (a) は名前や住所を作ってしまう。命に関わる場面で許されない

## 2026-11-07 Web とアプリの二本立て
- 比べた案: X（Android アプリ＋Navigation SDK）／Y（Web＋Google マップの URL）／Z（Web だけで地図と声の案内）
- 選んだもの: Web から開いた人は Y＋Z、アプリを入れた人は X。アプリの方が完成度が高い前提
- 選んだ理由: QR で開ける Web は入れる手間が無い。アプリは道を細かく指定でき、案内中も声の会話を続けられる
- 捨てた理由（今回は外す）: スマホの中で動くモデルとの声の会話（遅い・モデルを入れる手間）→ 今後の展望

## 2026-11-08 間に合うかの計算は気象庁の到達予想時刻を使う
- 比べた案: (a) 気象庁の到達予想時刻（潮位が変わり始める時刻・予報区ごと） (b) 府・市の想定（1m の津波が来る時刻。大阪市 最短約110分・堺市 約100分）
- 選んだもの: (a)。圏外で気象庁の電文が取れない時は、事前に保存した想定の一番早い値を使う
- 選んだ理由: 早い方＝安全側。(b) だと大阪ではほぼ全ての避難先が「間に合う」になり、計算する意味が見えない
- 捨てた理由: (b) は説明に使うだけにする

## 2026-11-08 歩く速さの基準
- 根拠: 消防庁「津波避難対策推進マニュアル検討会報告書」（平成25年3月）。1.0m/秒（老人の自由歩行・群衆・土地に不案内な人の歩行速度など）を目安とし、歩行困難者・身体障がい者・乳幼児・重病人などは 0.5m/秒に下がること、東日本大震災の実態調査の平均避難速度が 0.62m/秒だったことを考慮する（志摩市津波避難計画の引用で確認。報告書本文は文字が取り出せず未確認）
- 選んだもの（2026-11-08 更新）: 通常は **0.62m/秒**（東日本大震災の実際の平均避難速度）。「子どもが走れない」「歩くのがつらい」などでは 0.5m/秒。画面では「目安」と出す
- 選んだ理由: 旅行者は道を知らず、実際の災害では国の目安（1.0m/秒）より遅くなっている。安全側に寄せる
- 捨てた案: 通常を 1.0m/秒（国の目安）にする案。間に合わない避難先を「間に合う」と出す危険が大きい
- 未決: 坂道で速さを下げるか（志摩市は勾配で速さを補正している）
- 出典: https://www.city.shima.mie.jp/material/files/group/2/shimashi_tsunami_keikaku_P14-P37.pdf ／ https://www.fdma.go.jp/singi_kento/kento/kento106.html

## 2026-11-08 オンライン前提＋オフラインへの切り替え
- 比べた案: (a) オフラインだけで作る (b) オンラインで動くことを前提にし、通信が落ちたらオフラインに切り替える
- 選んだもの: (b)
- 選んだ理由: 津波の避難（数分〜数十分）の間は、混雑していてもデータ通信は残っていることが多い（東日本大震災では通話を 70〜95% 規制、データは規制なしか低い割合。基地局の停波が最多になるのは翌日〜数日後）。通信がある時は Gemini Live・Navigation SDK・Routes API・気象庁の到達時刻で一番良い案内をし、落ちたら端末内（Gemma 4・保存したデータ）が引き継ぐ。海外のハッカソン作品はオフライン専用で、この切り替えは無い
- 詳細: docs/demo-and-verification.md

## 2026-11-08 オンライン時の道案内は Navigation SDK をアプリの中で使う
- 比べた案: (a) Navigation SDK をやめ、「Google マップで案内」ボタンで Google マップに引き継ぐ (b) アプリの中で Navigation SDK
- 選んだもの: (b)。(a) のボタンは Web から開いた人向けに残す
- 選んだ理由: Google マップに移ると声の会話が途切れ、事前に用意した地域のデータ（浸水想定・避難先）も渡せない。浸水想定区域を避けた道を経由地で渡せる。案内開始時に 15〜20 分ぶんの経路を先に保存するので、途中で通信が切れても続く見込み（O3 で確かめる）
- 捨てた理由: (a) は Google マップのアプリ側の判断になり、浸水想定区域を避けられない

## 2026-11-09 圏外の会話は端末に合わせてモデルを切り替え、今回は小さいモデル＋ボタン
- 比べた案: (a) Gemma 4 E2B（約2.5GB） (b) FunctionGemma 270M（数百MB）を追加学習 (c) ボタンだけ
- 選んだもの: 端末に合わせて切り替える（Gemini Nano → Gemma 4 E2B → FunctionGemma → ボタン）。今回作るのは (b) と (c)
- 選んだ理由: 圏外の AI の仕事は「頼みごとを8種類から聞き分ける」だけで、大きいモデルは要らない。Gemma 4 E2B は多くの旅行者のスマホで動かない（チームの iPhone でも一番小さいモデルしか入らなかった）。届く人の数が効果になる。防災アプリは入れてもらいにくいので、重さも抑える
- 捨てた理由: (a) は今後の展望（余裕のある機種向け）。(c) だけだと自由な言い方を受けられない
- 追加学習: Gemini で多言語の言い方を作って FunctionGemma を学習させる（Gemini が先生、端末の小さい Gemma が生徒）。学習前後の正答率を言語ごとに出す

## 2026-11-09 上がる階は「3階以上」を下限にする
- 比べた案: (a) 浸水の深さから計算した目安だけ（1.0〜2.0m なら 2 階） (b) 津波避難ビルの指定基準（3 階以上）を下限にし、深い所は浸水の深さから上げる
- 選んだもの: (b)
- 選んだ理由: 堺市は 3 階以上の高さの建物を津波避難ビルに指定している。市の一覧に階の情報が無いので、指定基準に合わせるのが安全側。5m 以上は最上階・屋上
